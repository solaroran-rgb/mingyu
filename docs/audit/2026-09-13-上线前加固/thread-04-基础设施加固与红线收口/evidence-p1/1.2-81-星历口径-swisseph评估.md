## 3. astronomy-engine / celestine  vs  Swiss Ephemeris 对比

| 维度 | 现状（celestine + astronomy-engine 2.1.19） | npm `swisseph`（官方原生） | WASM 版 swisseph（如 swisseph-wasm 类） |
|------|------|------|------|
| 形态 | 纯 JS，零原生 | **Node 原生 C++ 插件** | WASM 模块 + 运行时加载 |
| 关键依赖 | 无 | `nan@^2.15`、`node-gyp@^8.4`（`npm view swisseph` 实测） | wasm 二进制 + `.se1`/`.eph` 数据文件 |
| Cloudflare Workers 可跑 | ✅ 已验证（edge Functions → core） | ❌ **硬不可行**：V8 isolate 不加载 `.node`、无 `fs` 读 `.eph`、无 node-gyp 构建 | ⚠️ 理论可跑，但需自行在 isolate 内 `WebAssembly.instantiate` 并把星历文件塞进 bundle/R2/KV |
| 数据文件 | 无需（级数内嵌） | 需磁盘 `.se1`/`.eph` | 需把数十~数百 MB `.se1` 内联或从 R2/KV 拉，冷启动与体积成本高 |
| 包体积/冷启动 | celestine 单包 ≈408KB，已入现有 chunk | n/a（Workers 跑不了） | wasm 约 1–2MB 起 + 数据文件，显著推高 edge 包体 |
| 精度 | 行星黄经 ~亚角秒级（VSOP87/ELP 截断级数）；celestine 自述对标 SE/JPL | SE 官方最高精度（理论基准） | 与原生 SE 同级 |
| API 映射 | 现状自洽：`calculateChart` / `Ecliptic(GeoVector(...))` | `swe_calc_ut`/`swe_julday`/`swe_set_ephe_path`……需整层重写 | 同原生 SE API，但要包一层异步加载 |
| 迁移 blast radius | — | 需改 astrolabe(A) + qi_zheng(B) + vedic(C)，三处 | 同左，另加 wasm/数据加载与构建管线 |

### 迁移成本与风险
1. **运行时硬阻断**：官方 `swisseph` 在 Cloudflare Workers 无法加载（原生 + fs），这一条单独即足以否决「直接换包」路线。
2. **WASM 路线代价不成比例**：要把 wasm + `.se1` 数据文件搬进 edge，需动构建（vite/wrangler manualChunks、Assets/KV/R2），引入冷启动延迟与包体压力；而现状纯 JS 后端对「回归黄经 ≤0.01° 判宫/星座」的需求精度已富余（亚角秒）。
3. **blast radius 与隔离红线冲突**：任务要求「模块隔离，只动星历计算层，不碰月令/半球反转（T-A 线程在做）」。一旦把 astrolabe 的星历后端换掉，会连带影响 B/C 两处证据源 id（`astronomy-engine-planets` / `astronomy-engine-true-node`）、大量断言这些 id 的测试（`qizheng-board`、`public-api`、`structured-output`）与证据文档，远超「只动星历层」的边界。
4. **红线性质**：1.2-81 是「版本文档化 + 可对质 + 确定性可复算」，本仓已钉版、已金标准、已证据化（线程-2 已判 partial→pass），**并非已观测到精度缺陷**。为一个已满足的文档化项引入运行时不兼容的依赖，收益为零、风险高。
5. 本仓 `docs/audit/vedic-phase2-decision.md` 已在 Phase 2 明确取舍：** deliberately 选纯 JS、拒绝第二星历源并存**，理由就是 Workers 无 wasm/原生 + 避免两套对质口径互相打架。本次评估与该既有决策一致。

## 4. 建议与理由（建议：不迁移）

**不迁移 Swiss Ephemeris 运行时，维持 `celestine@0.2.1`（西洋盘）+ `astronomy-engine@2.1.19`（七政四余/吠陀）+ 自研 Meeus/NOAA 低阶（节气核验）。**

理由：
- (a) Cloudflare Workers 下官方 `swisseph` 原生依赖**硬不可行**；WASM 路线为边际精度收益付出构建/包体/冷启动成本，**收益不抵风险**。
- (b) 现状后端已钉版、纯 JS、edge 已验证、金标准回归绿；行星黄经精度对宫位/星座判定富余。
- (c) 迁移 blast radius 与「模块隔离」红线冲突，且会扰动 T-A 线程正在处理的相邻模块。
- (d) 1.2-81 的合规义务（版本文档化、可对质、可复算）已由线程-2 证据 + 本评估满足；SE 关系以「对质口径」文档化，不进运行时。

### 后续可选项（不阻塞，留主控定夺，本次不做）
- 若未来需要「对标 SE 数值」的第三方对质，**在离线/CI 侧**跑一次 swisseph（Node 原生可在本地/CI 机跑）做批量对拍，把残差写进证据文档，而**不**把原生/wasm 塞进 edge 运行时。
- 若上云形态改为 Node 自建服务（脱离 Workers），再重评 WASM/原生 SE 的引入；当前 Pages+Functions 拓扑下维持纯 JS。
