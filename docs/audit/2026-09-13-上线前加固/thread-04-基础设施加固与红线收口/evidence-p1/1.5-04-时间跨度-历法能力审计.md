# 红线 1.5-04 · 时间跨度 —— 底层历法能力审计（公元前 3000 ~ 公元 5000）

- 线程：thread/p1-504-range（基于 thread/redline-p1-evidence）
- 日期：2026-09-13
- 依赖实测版本：tyme4ts **1.5.2**、astronomy-engine **2.1.19**、Node 22.23.2
- 裁决：**不放开输入口径，落边界**。维持交互输入 1900–2100、zodiac 流年 1900–2200，越界一律显式报错。

---

## 1. 红线要求

排盘支持**公元前 3000 至公元 5000** 年；**无法可靠计算的范围应显式报错**，不得静默错算。

## 2. 审计方法

不依赖库文档猜测，直接在 worktree 内用真实依赖跑探针：
- tyme4ts：`SolarTime.fromYmdHms(y, …)` 走完整四柱链路（公历→农历→年/月/日/时干支）；
  并直接构造 `LunarYear.fromYear(y)`、`SixtyCycleYear.fromYear(y)`；
- astronomy-engine：`MakeTime(y,…)` + 太阳黄经 `SunPosition`；
- 同时读取 tyme4ts 打包源码 `validateRange(...)` 的硬边界常量。

## 3. 实测结论（按体系）

### 3.1 中文命理核心：tyme4ts（四柱 / 农历 / 节气 / 干支 / 生肖）

源码硬边界（`node_modules/tyme4ts/dist/lib/index.mjs`）：

| 类 | 校验调用 | 允许区间 | 含义 |
|---|---|---|---|
| `SolarYear` / `SolarTime` / `SolarMonth` / `SolarDay`（公历入口） | `validateRange(year, 1, 9999)` | **公元 1 ~ 9999** | 四柱链路实际走的入口 |
| `LunarYear`（农历年） | `validateRange(year, -1, 9999)` | -1 ~ 9999 | -1 = 天文纪年 0 = 公元前 1 年 |
| `SixtyCycleYear`（六十甲子） | `validateRange(y, -1, 9999)` | -1 ~ 9999 | 同上 |
| `RabByungYear`（藏历） | `validateRange(year, 1027, 9999)` | 1027 ~ 9999 | 仅藏历 |
| `HijriYear`（回历） | `validateRange(year, -640, 9666)` | -640 ~ 9666 | 仅回历 |

实测探针输出：

```
SolarTime.fromYmdHms(y, 6, 15, 12) 走四柱：
  y=-4000  →  illegal solar year: -4000
  y=-3000  →  illegal solar year: -3000
  y=-1000  →  illegal solar year: -1000
  y=-1     →  illegal solar year: -1
  y=0      →  illegal solar year: 0
  y=1      →  正常，年柱 辛酉
  y=2024   →  正常，年柱 甲辰
  y=5000   →  正常，年柱 庚辰
  y=5001   →  正常，年柱 辛巳
  y=6000   →  正常，年柱 庚申
  y=9999   →  正常，年柱 己亥
  y=10000  →  illegal solar year: 10000

LunarYear.fromYear(y)：
  y=-3000  →  illegal lunar year: -3000
  y=-1000  →  illegal lunar year: -1000
  y=1900/2024/3000/4000/5000 → 正常（含闰月表）

SixtyCycleYear.fromYear(y)：
  y=-3000  →  illegal sixty cycle year: -3000
  y=-100   →  illegal sixty cycle year: -100
```

**判定：**
- **任何公元前（负年）的四柱、农历、节气、干支、生肖都无法计算。** 公历入口 `SolarTime` 直接拒绝 year ≤ 0，这是库的硬约束，改项目配置/校验无法绕过。农历与干支虽在内部直接构造时放到 -1（= 前 1 年），但四柱链路走公历入口，仍要求 ≥ 公元 1 年。
- **上沿：tyme4ts 结构可算到公元 9999**，红线 +5000 落在其内，实测 5000/9999 均能排出干支四柱。
- 注意：远年（如 5000）农历/节气由 ShouXingUtil 多项式朔望外推，**能算但天文精度随年代递减**，属“结构可用、金标准未覆盖”，不等于观测级准确。

### 3.2 西方占星星历：astronomy-engine（七政 / Vedic）

```
MakeTime(y, 6, 15, 12) + SunPosition 太阳黄经：
  y=-3000 → 正常返回（黄经 201.6°）
  y=-1000 → 正常返回（16.7°）
  y=0     → 正常返回（280.4°）
  y=1     → 正常返回（281.4°）
  y=2024  → 正常返回
  y=5000  → 正常返回
  y=10000 → 正常返回
```

**判定：** 西方占星路径（`qi_zheng`、`vedic`）**结构上可算公元前**，不抛错、不 NaN。但其 VSOP87/ELP2000 解析级数是截断多项式，年代越远长期误差越大，仅可作“能出结果”的降级路径，精度需标注为长期外推。

### 3.3 自研天文时间尺度：`calendar/astronomical-time.ts`

- `estimateDeltaTSeconds(decimalYear)`：`decimalYear < 1900 || >= 2201` 直接抛 `ΔT 估算年份需在 1900-2200 之间`（Espenak-Meeus 分段多项式）。
- `buildAstronomicalTimeEvidence(input)`：`input.year < 1900 || > 2200` 抛 `天文时间尺度证据当前支持 1900-2200 年`。

**判定：** 时间尺度 / ΔT 证据层硬限 1900–2200，越界即显式抛错。

## 4. 可行性结论

| 红线子区间 | 中文四柱/农历/节气 | 西方占星星历 | ΔT 时间尺度证据 | 结论 |
|---|---|---|---|---|
| **-3000 ~ -1（公元前）** | ❌ 全部抛错（tyme4ts 硬下限 公元 1） | ✅ 结构可算（长期外推） | ❌ 抛错 | **不可满足**：中文命理根本算不出 |
| 1 ~ 1899 | ✅ 可算（金标准未覆盖） | ✅ | ❌ 抛错 | 输入层保守拦 |
| 1900 ~ 2100 | ✅ | ✅ | ✅ | **当前稳定支持区间** |
| 2101 ~ 2200 | ✅ | ✅ | ⚠️ 外推 | zodiac 流年口径 |
| 2201 ~ 5000 | ✅ 结构可算（精度递减） | ✅ | ❌ 抛错 | 未验证，输入层保守拦 |

**因此红线“-3000 ~ +5000”无法在当前技术栈下整体兑现：**
- 下沿 -3000 是硬伤——中文命理链路在 year ≤ 0 直接抛 `illegal solar year`，放开输入只会让排盘崩在运行时，违背红线“显式报错而非静默错算”的本意；
- 上沿 +5000 虽结构可算，但 ΔT 证据层与西方星历精度均进入未验证外推区，收益不抵风险。

## 5. 决策与落地

**决策：不放开输入口径，落边界。** 维持现有保守闸门，越界一律在输入层显式报错：
- 交互输入 `getBirthDateValidationMessage`：**1900–2100**（`calendar/date-validation.ts`）；
- 生肖流年 `resolveYearGanZhi`：**1900–2200**（`zodiac/index.ts:241`）；
- 历法原语 `daysInGregorianMonth`：**1–9999**（不变）。

**未改动：** 校验范围、API schema、前端 i18n 文案一律不动（放开分支才需改）。

**测试：** `tests/1.5-04-date-range.test.ts`
- 头部注释记录本次实测裁决与结论指针；
- 新增红线下沿 `-3000` 必须显式报错的断言（越界只增不减）。

**降级 / 未来方案（如需真正支持公元前）：**
1. 中文四柱/农历：需替换 tyme4ts 的公历入口下限（fork/patch 或换支持天文纪年的农历引擎），是另一个量级工程，不在本红线内；
2. 短期可降级：公元前输入 → 显式报错并提示“中文命理暂不支持公元前”；仅西方占星（astronomy-engine）可作 BC 降级候选，但需标注长期外推精度。

## 6. 残留风险

- **红线未完全兑现**：-3000 ~ 1899 与 2101 ~ 5000 仍被输入层拒绝，与红线字面区间不符；已按“无法可靠计算则显式报错”这一安全口径收口，属已知偏差，需产品/红线 owner 确认接受。
- 远年（>2200）农历/节气虽不抛错，但 ShouXingUtil 外推精度无金标准背书，当前靠输入层拦截规避。
- astronomy-engine 的 BC 结果未经观测/星历表交叉验证，仅证明“不崩”，不证明“准”。
