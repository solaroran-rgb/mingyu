# T4-S2 · 根因分析（503/1102、500 INTERNAL_ERROR、400 契约）

> 时间：2026-09-13 05:00｜执行者：ZCode｜证据：`01_503复现记录.md`、`repro_conflict.mjs`（含堆栈）、源码对勘

## A · 主问题：Worker 503 = CF Error 1102（CPU 超限）

### 证据链

1. 503 body = `error code: 1102`，无应用层 JSON 包装 → 未进 handler，Worker 运行时杀死。
2. 同一输入交替 503/200（5 连测 503,200,503,200,503）→ 非确定性计算超时，是**每次请求独立计量的 CPU 预算竞争**。
3. 503 快败（median 370ms）/200 慢成（median 555ms–3.6s）→ 被杀发生在初始化/前段阶段。
4. 本地 Node 直跑同 10 组样例（`run_local.mjs`）全 OK → 计算逻辑正确，仅运行时资源约束问题。
5. 503 率与端点计算量正相关（ziwei 55% > qimen 50% > bazi 40% > liuren 20%）。

### 根因判定（高置信）

`src/lib/public-api/handler.ts` 顶部**静态 import 全部 21 体系**（bazi/ziwei/iztro/qimen/liuren/meihua/xiaoliuren/jinkoujue/astrolabe/tarot/lenormand/qizheng/xuankong/taiyi/wuyun-liuqi/huangji-jingshi/bazhai/almanac/vedic…）。CF Pages Functions 将其打进单一 Worker bundle：**每个请求（无论打哪个端点）都要先付出全部 21 体系的模块初始化 CPU**（含 iztro 安星表、astronomy-engine 星历表、历法表等重数据结构的顶层求值）。冷 isolate 上这笔 CPU + 端点本身的计算 ≈ 超过 per-request CPU 预算 → 1102；热 isolate（模块已初始化、JIT 已热）则压线通过 → 200。这解释了间歇性与「越重的端点越容易死」。

> CF 限额参考：Workers 免费档 10ms CPU/请求，付费档 30s。线上现象（约 1/3 死亡率、快败）与「接近小额预算上限、随机器负载抖动」吻合。当前账户套餐需主控在 CF 控制台确认（S3-A 修复不依赖此确认）。

### 修复策略（按任务卡 S3 顺序，最短路径优先）

1. **【首选】handler 按端点延迟加载**：把 21 体系的静态 import 改为在各 case 分支内 `await import()`，每个端点只付自己的模块初始化成本。预估：ziwei 请求不再初始化 qizheng/astrolabe/tarot…，冷启动 CPU 降一个量级。
   - 风险：`@temposoul/core` barrel 导入会连带拉全部子模块 → 须改从子路径导入（core 已有 `/bazi` `/ziwei` `/calendar` 等子导出，treeshake 线程 g6 已验证子路径导入可行）。
   - 影响面：仅 `handler.ts` 与 `prompt-builders.ts` 的 import 结构，业务逻辑零改动。
2. 备选（若 1 不足）：真太阳时/历法结果 KV 缓存去重；超时输入返回结构化降级响应。
3. 兜底：CF 控制台确认套餐/提升限额（花钱项，须主控批示）。

**禁止**：直接部署线上。修复走 `thread/t4-infra`，本地 `wrangler pages dev` 或 `vitest`/`test:api` 验证，部署归主控。

## B · 确定性 bug：时区冲突/回拨歧义 → 500（应 400）

### 复现

线上：`POST /api/v1/bazi/calculate`，`timezone=8` + `timeZoneId=America/New_York` → 500 INTERNAL_ERROR（4/4，100%）。
本地（`repro_conflict.mjs`）：

```
FAIL 冲突 timezone=8 + NY: Error: timezone 固定偏移 UTC+8 与 America/New_York 在该当地时刻的历史偏移不一致。
    at resolveCivilTime (packages/core/dist/calendar/civil-time.js:87)
    at convertTrueSolarTime (true-solar-time.js:496)
    at resolveTrueSolarBirthTime (true-solar-time.js:619)
    at BaziCalculator.calculateBazi (baziCalculator.js:384)
```

### 根因

`packages/core/src/calendar/civil-time.ts` `resolveCivilTime()` 两处校验抛**原生 `Error`**：

- L133：夏令时回拨歧义且未提供 timezone（`status === 'ambiguous'`）；
- L138：timezone 固定偏移与 IANA 历史偏移冲突（`offsetConflict`）。

`handler.ts` `handleError()` 只识别 `ApiError` / `MingyuCoreError`，原生 Error 落入兜底 `500 INTERNAL_ERROR`。而该端点 OpenAPI schema 明确承诺「timezone 与 timeZoneId 冲突时拒绝计算」（预期 400）。属**错误分类违约**：用户输入问题被当成服务端内部错误。

### 修复（最短路径）

将上述两处 throw 换为 `MingyuCoreError({ category: 'validation' })`（handler 已有映射：validation → 400），对齐 `true-solar-time.ts` 既有用法（`INVALID_FIELD_RANGE` 等先例）。不新增机制、不改 handler。

> 同文件/同层其余 ~50 处原生 throw（51 处/ calendar 目录）**不在本次修复面**：多数路径上层已有包装（如农历不存在 → 400 正常），盲目全改违反最短路径且扩大回归面。登记进 S4 红线排期表逐项甄别。
