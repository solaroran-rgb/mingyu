## 1. CF Pages 根域（apex）支持机制（以 CF 官方文档为准）

核心事实（来源见文末引用）：

1. **Cloudflare Pages 支持裸域直接绑定**，但前提是该域名的**权威 DNS 托管在 Cloudflare**（full setup，即 NS 已委派给 CF）。
   此时 CF 利用 **CNAME flattening** 在 zone apex 合成一条指向 `temposoul.pages.dev` 的被代理 CNAME，橙色云开启，全球 anycast + 自动证书全部生效。
   > 官方原文：“CNAME flattening … allows you to use a CNAME record at your zone apex … This functionality is also what allows you to use a root custom domain with a Cloudflare Pages site.”

2. **DNS 不托管在 CF（partial setup / CNAME setup）时，apex 无法走 CF 代理**：
   - 你的权威 DNS 必须原生支持 CNAME flattening 或 ALIAS/ANAME 记录，否则 apex 只能写 A/AAAA；
   - 阿里云云解析**不提供** ALIAS/ANAME，也不支持 apex CNAME flattening；
   - 在 apex 直接写 A 记录指向 CF 的共享 anycast IP（如 `104.21.x.x` / `172.67.x.x`）**官方明确不推荐**：标准 anycast IP 会变动，且 zone 不在 CF 时边缘节点无法把请求路由到 Pages 项目（会 522/530）。官方仅对购买 Static IPs / BYOIP 的付费企业客户推荐该做法。

3. **301 落点**：一旦 apex 已作为自定义域绑到 Pages 项目，apex→www 的 301 可在 CF 边缘完成，三种等价做法任选其一：
   - Pages 静态规则 `public/_redirects`（随部署上线，版本化管理，推荐）；
   - 单条 **Redirect Rule**（Ruleset，仪表盘/Terraform 可配）；
   - 旧版 Page Rule（免费版仅 3 条，已被 Redirect Rules 取代，不推荐新增）。

## 2. 三方案对比

| 维度 | 方案 A：NS 迁到 CF（推荐） | 方案 B：DNS 留阿里云 | 方案 C：CF 专业版 $20/月 |
|---|---|---|---|
| 做法 | Cloudflare Add Site 接管 `temposoul.com` zone；迁移现有全部阿里云记录；Pages 项目加 apex 自定义域；`_redirects` 做 apex→www 301 | B1：阿里云「显性 URL 转发 301」`@ → https://www.temposoul.com`；B2：`@` 写 A 指向 CF anycast IP（不推荐） | 与 A 完全相同的 NS 迁移路径，仅升级 Pro 套餐换取更多 Ruleset 配额与 WAF |
| 费用 | **免费** | **免费**（B1）/ 不产生 CF 费用 | **$20/月** |
| apex 可达性 | ✅ CNAME flattening，稳定、官方支持 | B1：⚠️ 见「致命前提」；B2：❌ 官方不推荐，zone 不在 CF 时大概率 522 | ✅ 同 A |
| HTTPS / 自动证书 | ✅ CF 边缘自动签发 | B1：转发服务器在中国大陆，证书由阿里云转发层终止，体验与 SLA 均弱 | ✅ 同 A |
| 致命前提 | 需把阿里云现有全部记录（MX / TXT / www / 邮箱验证等）迁到 CF，NS 切换期间全量生效 | **B1 要求被转发域名已完成 ICP 备案**（转发服务器在中国大陆）。本项目为「国学出海」面向海外，通常无 ICP 备案 → **B1 事实上不可行**；URL 转发亦不保证 SLA、不支持泛解析 | 无额外前提，纯属加钱 |
| 301 实现 | `public/_redirects` 或 1 条 Redirect Rule（本线程已落盘，见 §4） | 阿里云控制台勾选 301 | 同 A，规则数更宽裕 |
| 风险 | 一次性 NS 迁移（TLL 生效数小时~48h）；迁移漏记录会影响邮箱/验证 | B1：备案风险、大陆转发节点、出向海外访问慢；B2：anycast IP 漂移导致 apex 挂站 | 无新增技术风险，仅成本 |
| SEO | ✅ 原生 301，权重传递标准 | B1：301 语义可传递，但链路多一跳大陆节点 | ✅ 同 A |

### 推荐结论

**推荐方案 A（NS 迁到 Cloudflare，免费版）。**

理由：
- 这是 CF 官方为 Pages apex 自定义域设计的唯一稳定路径；
- 零月费，HTTPS、全球 anycast、301 全部在 CF 边缘完成；
- 方案 B 的唯一可行子路径 B1 卡在「ICP 备案」硬门槛上，与本项目出海定位冲突；B2 是官方明确不推荐的反模式；
- 方案 C 对「单条 apex→www 301」是过度付费，免费版 Redirect Rules 配额已足够；未来若需要更多 WAF / Bot 管理 / 图片优化再升级不迟。

> 待用户决策点：是否接受把 `temposoul.com` 的权威 DNS 从阿里云迁到 Cloudflare（影响面：该域名下所有现有 DNS 记录与邮箱服务，需先迁移核对）。

## 3. 方案 A 落地前置检查清单（线上执行前逐项打勾）

1. 在阿里云云解析控制台**完整导出/截图现有全部记录**：`www` CNAME、MX（如有企业邮箱）、TXT（SPF / 域名验证 / 其他服务商验证）、CNAME（如 CDN / 第三方服务验证）、`@` 现有记录。
2. Cloudflare 控制台 → Add Site → 输入 `temposoul.com` → 选 **Free** 计划；CF 会自动扫描并导入可识别的记录。
3. **人工逐条核对**自动导入结果，重点：MX / TXT / 任何邮件相关记录不得丢失、不得误改。
4. Pages 项目 `temposoul` → Custom domains → Add `temposoul.com` → CF 自动在 zone 生成 apex 代理 CNAME（flattening），状态变 Active。
5. 切 NS：把阿里云域名注册商处的 nameserver 改为 CF 提供的 2 个 NS（如 `*.ns.cloudflare.com`）。
   - NS 生效期：通常数小时，最长 48h；期间新旧 NS 均可用，双跑不中断。
6. 部署本线程落盘的 `public/_redirects`（随下次 Pages 构建自动上线），验证 `https://temposoul.com/*` 返回 `301` 且 Location 指向 `https://www.temposoul.com/*`。
7. 收尾：Cloudflare → SSL/TLS → Edge Certificates → 开启 **Always Use HTTPS**；确认 HSTS 策略（按需）。

## 4. 已落盘的可执行规则文件（未部署，待决策后随构建上线）

### 4.1 `public/_redirects`（Pages 静态重定向，推荐主用）

语法参考 CF 官方 `/_redirects` 文档。内容（已落盘，UTF-8 无 BOM）：

```
# TempoSoul · 根域 → www 全站 301（方案 A 上线后生效）
# 官方语法: https://developers.cloudflare.com/pages/configuration/redirects/
https://temposoul.com/*  https://www.temposoul.com/:splat  301!
```

- `:splat` 保留原路径与 query string（由 `_redirects` 自动透传）；
- 末尾 `!` = forced，不覆盖已存在的路由/函数；
- 该文件位于 `public/`，Vite 构建时原样拷贝到 `dist/`，Pages 边缘即生效；
- 本机 `wrangler pages dev` / 线上均可用；**本线程未执行 deploy**。

### 4.2 CF Redirect Rule 脚本（备选 / 兜底）

已落盘 `docs/governance/assets/cf-apex-to-www-redirect-rule.json`（仪表盘 Rules → Redirect Rules 可直接对照创建，或用 Terraform `cloudflare_ruleset` 资源以同表达式落盘）。表达式与动作：

- 表达式：`(http.host eq "temposoul.com")`
- 动作：`redirect` → `dynamic` → `concat("https://www.temposoul.com", http.request.uri.path, http.request.uri.query)`，status `301`，preserve query string。

二者**二选一**即可；同时存在时以更具体的规则为准，建议只启用 `_redirects`，Redirect Rule 作为 NS 迁移完成前的备选预案。

## 5. 方案 B（DNS 留阿里云）逐步操作文档 —— 仅作备案/对照，不建议执行

> 前置硬门槛：`temposoul.com` 必须已取得 ICP 备案号（转发前、转发后域名均需可核验）。本项目出海定位，**默认不满足**。若未来补备案后再考虑，步骤如下：

1. 登录阿里云控制台 → 云解析 DNS → 域名 `temposoul.com` → 解析设置。
2. 确认 `www` 记录已存在且为 `CNAME → temposoul.pages.dev`（不动）。
3. 新增记录：
   - 记录类型：**显性 URL 转发**；
   - 主机记录：`@`；
   - 记录值：`https://www.temposoul.com`；
   - 转发类型：**301（永久）**；
   - TTL：默认 10 分钟。
4. 保存后等待 5–10 分钟，用 `curl -I http://temposoul.com` 验证返回 `301` 且 `Location: https://www.temposoul.com/...`。
5. 风险提醒：URL 转发不承诺 SLA；不支持泛解析；转发服务器在中国大陆，海外访客首跳略增延迟；备案失效会 502。

## 6. 风险与回滚（方案 A 主线）

### 6.1 切换期间风险

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 解析延迟 / 新旧记录并存 | NS 切换后 TTL 未过期，最长 48h | 切换前把 CF 与阿里云 TTL 都调到 300s；期间双跑，www 不受影响 |
| 漏迁 MX / TXT 记录 | 自动导入遗漏邮件/验证记录 | §3 第 1、3 步逐条核对；切换前先用 `dig` / 在线工具验 |
| apex 自定义域验证卡 Verifying | Pages 未先在 dashboard 绑定就手改 DNS | 严格按 §3 顺序：先在 Pages Add 域，再切 NS |
| 301 误伤 www 自身 | `_redirects` 写成通配 | 规则仅匹配 `http.host == temposoul.com`（裸域），www 不受影响 |
| 缓存旧 301 | 浏览器/CDN 缓存 | 301 被浏览器强缓存；先在 staging 域或 `curl -H 'Cache-Control: no-cache'` 验证 |

### 6.2 回滚步骤（任意一步出问题）

1. **NS 回滚**：把注册商处 nameserver 改回阿里云原 NS（如 `dns1.hichina.com` / `dns2.hichina.com`），等待 TTL 过期（最长 48h，通常数十分钟）。
2. **Pages 侧**：Pages 项目 → Custom domains → 移除 `temposoul.com`；不影响 `www` 与 Pages 项目本体。
3. **规则回滚**：删除 `public/_redirects`（或把该单行注释掉），随下次构建自动失效；若用了 Redirect Rule，在 Rules 面板 Disable / Delete。
4. **数据无损失承诺**：本方案不改动内容、不改后端、不动 KV；DNS 层回滚后线上即恢复到「仅 www 可访问」的现状。
